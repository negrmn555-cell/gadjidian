# Четвёртый этап: заметки, полный импорт и память чата

Дата: 2026-10-03. Выполнены три пункта из запроса пользователя. Исходники предыдущих этапов сохранены.

## Заметки и люди

- В области задач есть «Добавить заметку» и «Заметки и люди». Поиск работает по имени,
  названию, пути, меткам и aliases; фильтр — по типу заметки.
- Ручная форма: название, тип (заметка / идея / человек), категория, текст Markdown,
  метки и ключевые слова. Для человека: другие имена, телефон, email, роль/должность.
- Редактор заменяет старые факты, позволяет работать с полным Markdown/YAML и показывает
  безопасный предпросмотр без выполнения HTML. Из чата заметки открываются по кнопке результата
  или источника, из памяти — по связанному источнику.
- Структурированные правки сохраняют неизвестные YAML-поля и комментарии. ID и путь
  не меняются при изменении названия. Старой заметке без ID он добавляется при сохранении.
- Сохранение требует expectedContentHash и operationId. Устаревшая версия возвращает 409;
  черновик остаётся в форме, доступна актуальная версия для сравнения и явного объединения.
  Удалённая заметка не создаётся заново редактированием. Повтор операции не создаёт копию.
- `/person` ищет также ручные карточки по title/aliases, при тёзках требует выбор пути.
  Свободный запрос ИИ может исправить факт через update_note, только после полного read_note
  и с hash прочитанного содержимого. Неизвестные/служебные YAML-поля защищены от удаления,
  комментарии переносятся из старого документа. Заметки длиннее 12 000 символов ИИ не заменяет
  целиком по обрезанному чтению — доступен ручной редактор.
- Управляемые задачи, приватные и служебные папки не доступны для записи редактором заметок.
  Преобразование задач и изменение их полей относятся к следующему этапу задач.

Контракты: NoteCreateInput, NoteRecord, NotePage, NoteEditInput, NoteWriteResult.

| API | Контракт |
| --- | --- |
| GET /api/notes?q=TEXT | NotePage: metadata + invalidRecords |
| GET /api/notes/document?path=PATH | NoteRecord: поля, body, полный content, contentHash |
| POST /api/notes | { note: NoteCreateInput, operationId } → NoteWriteResult |
| PATCH /api/notes/document | { path, edit: { fields } или { content }, expectedContentHash, operationId } |

## OCR и полный импорт

- Плюс по-прежнему загружает фото/документы. Рядом с вложением есть «Полностью в заметку»;
  такую же операцию можно вызвать для вложения ранее отправленной реплики до истечения TTL.
- OCR русский + английский выполняется локальным Tesseract.js. Модели поставляются npm-пакетами,
  в запросе нет обращения к CDN или внешнему OCR. PDF.js рендерит страницы для OCR через
  локальный canvas. Документация: [Tesseract.js API](https://github.com/naptha/tesseract.js/blob/master/docs/api.md),
  [локальная установка](https://github.com/naptha/tesseract.js/blob/master/docs/local-installation.md),
  [PDF.js Node rendering](https://github.com/mozilla/pdf.js/blob/master/examples/node/pdf2png/pdf2png.mjs).
- PDF обрабатывается постранично. Текстовые страницы извлекаются напрямую; сканы и страницы
  с изображениями проходят OCR целиком, чтобы не пропустить текст внутри графики и не
  продублировать текстовый слой. Отчёт содержит метод и уверенность каждой страницы.
- Для DOCX извлекаются основной текст, строки/ячейки таблиц, колонтитулы, сноски и обычные
  PNG/JPEG/WebP-изображения. Встроенные объекты/неподдерживаемая графика перечисляются как
  доступные только в оригинале; импорт получает статус partial.
- TXT/MD/CSV/JSON сохраняются полностью в пределах лимита извлечённого текста. Длинный
  документ не пропускается через ИИ и не обрезается до лимита контекста разговора.
- Полный импорт пишет исходные байты в `_attachments/asset_HASH/original.EXT`, извлечённый
  текст — в Markdown категории, картинки DOCX — рядом с оригиналом, manifest.json — с SHA-256,
  версией extractor, языками, покрытием страниц/разделов, предупреждениями и checksums файлов.
- `complete` означает обработку всех частей, не безошибочность OCR или сохранение оформления.
  `partial` явно отображается. Таблицы — текстовые строки, оформление/графика PDF доступны
  в оригинале. Низкая уверенность OCR требует сверки и перечисляется в отчёте.
- Оригинал скачивается из редактора через авторизованный маршрут. Перед выдачей проверяются
  постоянные файлы и checksums; исходник не исполняется сервером.
- Оригинал/заметка/manifest не удаляются при очистке чата или истечении временного вложения.
  Один исходный checksum и версия обработки создают один asset даже при повторной загрузке
  под другим именем. Изменённая вручную импортированная заметка при повторе не перезаписывается.

Лимиты: 5 МБ исходного файла, 100 страниц PDF, 16 млн пикселей изображения (проверка заголовка
до декодирования), 1 млн символов извлечённого текста; 25 МБ выбранных распакованных частей DOCX.
Анимированный WebP не поддерживается. На устройство — 50 МБ временных байтов/текста/отчётов;
не более двух загрузок/импортов одновременно на сервере и одной на устройство. Контекст ИИ
по-прежнему ограничен 80 000 символов: большие документы импортируются через отдельную кнопку.
Парсинг/OCR идёт в отдельном процессе, лимит JS heap 512 МБ, таймаут 180 секунд; завершение
процесса прекращает его OCR-потоки. Native canvas также ограничен размером поверхности,
но полная ОС-изоляция ресурсов контейнером остаётся эксплуатационной задачей.

Некорректный/зашифрованный документ, неприемлемый размер, ошибка декодера или общий таймаут
дают контролируемую ошибку до импорта. Ошибка отдельной страницы отражается в partial-отчёте;
оригинал такой операции сохраняется полностью. При частичном распознавании фото без текста
его всё равно можно импортировать с предупреждением. Для обычного разговора доступен OCR-текст
без vision; для анализа самого изображения нужен профиль с vision.

Контракты: ExtractionPage, ExtractionReport, ImportResult.

| API | Контракт |
| --- | --- |
| POST /api/attachments?chatId=ID&name=NAME | Байты → Attachment + краткий extraction status |
| POST /api/attachments/:id/import | { chatId, note: {title, category}, operationId } → ImportResult |
| GET /api/assets/:id/original | Авторизованная выдача постоянного оригинала, Content-Disposition attachment |

## Журнал многофайловой записи

Миграция основной SQLite №4 добавляет vault_batches. План и все исходные байты сохраняются
до записи файлов. Общая очередь Git/записи проверяет все base hashes, выполняет атомарную
замену каждого файла и записывает manifest последним. Checksums повторно проверяются перед
заменой/коммитом. Коммит включает только пути этой операции, чужие staged-файлы остаются отдельно.

После сбоя prepared-план восстанавливает оставшиеся файлы. Найденный Git-коммит операции
не повторяется и не перезаписывает более поздние изменения. Конфликт останавливает операцию,
сохраняет чужое содержимое и сообщает необходимость проверки локального результата.
Завершённые payloads удаляются из журнала; постоянные данные остаются в vault/Git.
Публикация использует прежние retries Git; receipt различает saved_local / committed / synced.

Это восстановимая операция с атомарной заменой отдельных файлов, а не транзакция файловой
системы для всех внешних программ: Obsidian может увидеть промежуточные файлы во время сбоя.
Сервер выдаёт постоянные assets только с полным проверяемым manifest; сортировка не реализована.

## Память чата

- У каждого чата есть краткое резюме и ссылки на прочитанные/изменённые заметки. В интерфейсе
  «Память чата» показывает резюме и состояния источников; «Обновить резюме» пересобирает его.
- Автоматическое резюме использует снимок выбранного чат-провайдера без tools. Если ИИ не
  настроен или суммаризация не удалась, хранится короткая локальная выдержка. Ошибка summary
  не скрывает уже сохранённую заметку/задачу и не повторяет запись.
- Summary хранит точные IDs и hashes обобщённых реплик, не только верхний ID. Генерация не
  может сама объявить покрытие. Реплики, прибывшие после снимка, остаются вне его покрытия.
- В контекст передаются summary, последние необобщённые реплики и реестр источников.
  Обработка ограничена 32 репликами на chunk, до четырёх chunks за проход; при отставании
  контекст явно сообщает о необобщённых репликах. Полная история остаётся доступной пользователю.
- read/search записывают hash реально прочитанной версии и note ID, если он есть. Перед ответом
  и открытием памяти сравниваются текущие hashes после Git pull. Изменение/удаление сбрасывает
  прежнее резюме; старый ответ по этому источнику исключается из модельной истории.
- Перемещение ищется по устойчивому ID. При дублированном ID нельзя угадывать карточку.
  У старого файла без ID удаление/перемещение отражается как недоступный источник.
- Новая версия принимается только после нового чтения/записи. Summary — кэш разговора,
  не самостоятельный источник актуальных фактов. Источники ограничены 64 последними;
  при вытеснении summary сбрасывается, неизвестные старые версии не считаются актуальными.
- Новая задача по-прежнему не получает дедлайн из summary/старой задачи: режим задач
  работает с текущим запросом и собственным активным draft.
- Резюме, hashes источников и coverage находятся в *.chats.sqlite. TTL не продлевается
  пересборкой и не превышает срок исходного чата/самой ранней покрытой реплики. Очистка
  истории удаляет память; точная граница проверяется при чтении.

Контракты: ChatMemory, MemorySource; GET /api/chats/:id/memory — проверка и чтение,
POST /api/chats/:id/memory — суммаризация. Только app-key своего чата; quick-key не подходит.

## Проверки и оставшаяся работа

- 75 тестов: 17 core + 58 server. Проверены редактор, YAML/comments, конфликт версий,
  неизменность ID, alias/ties, ограничение AI read-before-edit, полный импорт и дедупликация,
  Git commit/recovery, исключение чужого staged-файла, реальные русско-английские OCR и
  смешанный PDF, DOCX, exact summary coverage, TTL, удаление/перемещение/изменение источника,
  изменение во время суммаризации и авторизация API/download.
- Production-сборка включает проверку типов; мобильный UI проверен на 390×844 и 320×740.
  Через интерфейс создана/исправлена карточка, фото распознано и импортировано, а изменение
  карточки сбросило прежнее резюме. Оригинал побайтно проверен через HTTP после очистки чата.
  IAB не сообщил событие blob-download при UI-клике; HTTP-выдача проверена, сохранение файла
  на конкретном мобильном браузере следует проверить при развёртывании.
- Проверки используют отдельные temp-vaults и data/development-preview, без реальных
  пользовательских документов, платных моделей и SMS. Примерные записи UI удаляются после QA.
  Снимки: stage4-person-editor.png, stage4-ocr-import.png, stage4-memory-invalidated.png.
- OpenCode CLI openai/gpt-6.1-sol/high/plan независимо исследовал десять сценариев ошибок,
  без чтения/передачи исходников. Вывод проверен; TTL резюме ограничен 14 днями независимо
  от предложений исследователя. OpenCode не изменял файлы. Ревью приватных исходников
  остаётся отдельным ранее не разрешённым действием.
